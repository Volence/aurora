## 2. Do the shapes truly match? Yes, with three differences, each handled

The document is `{schema, ok, refusals: [{rule, subjects, message}], warnings}`, built by the same
`clip_manifest.refusal_record` / `json_text` in aeon. So `src/core/formats/donors/clip-validate-json.ts`
now has ONE reader, `readClipToolJson(tool, exitCode, stdout, stderr)`, and two entrances,
`readValidateJson` and `readBakeJson`. Nothing is duplicated. What differs:

1. **Schema.** The bake's `schema` is its own `BAKE_JSON_SCHEMA` (1), bumped independently of validate's.
   The reader holds each tool to its own constant (`BAKE_JSON_SCHEMA` beside `VALIDATE_JSON_SCHEMA`).
2. **Rule vocabulary.** The bake adds `C1`..`C3`, `FG_PAGE_BUDGET` and more `null`s (plus every loader tag,
   since a `ClipManifestError` reaches the bake too). All are strings or null, which is all the reader
   requires; only C1 names a clip, the rest are about the act as a whole.
3. **A refusal can come after the tree is written** (`--expect-worst`, the page budget): aeon's `ok: false`
   means "do not use that tree". Aurora's channel (`src/main/clip-tool.ts`) reads the tree only on exit 0,
   and the page uses it only when the reader says `accepted`; an exit-0 bake with no JSON is a crash and
   its tree is not used.

The only wording difference is the tool's name in a crash's `why` ("aeon's bake exited 1 and printed no
JSON: it crashed, so the act was NOT judged").

## 3. What the page does now

- The bake argv ends in `--json` (`clipToolArgv`).
- **Paste, bake stage** (`src/renderer/state/donor-paste.ts`): could-not-run first (unchanged), then
  `readBakeJson`. A refusal is `{kind: 'refused', stage: 'bake', refusals, warnings, text, command}` and is
  rendered exactly like the loader's (rule tag, subjects, aeon's sentence, warnings) under "aeon's bake
  refused this paste, so nothing was written". A crash is `{kind: 'crashed', stage: 'bake', ...}`, rendered
  "aeon's bake CRASHED (exit N), so this paste was not judged and nothing was written. This is not a
  refusal: <why>" with stderr, stdout and the command. Both stages now build these outcomes through one
  `judgedOutcome`, so the loader's fields are byte-for-byte what its inline branch built before.
- **Target act re-bake note** (`refreshBake`): gains `bakeNoteKind` (`refused` / `crashed` /
  `could-not-run`). A refusal note lists `R7 (clip 1 cpz_s2): <message>`; a crash note says CRASHED, "This is
  not a refusal", and carries stderr; the DOM carries it as `data-donors-bake-note="<kind>"`, and the debug
  probe (`src/renderer/debug-hooks.ts`) as `paste.bakeNoteKind`.
- **Not touched:** `withClip` and the manifest writer (row 222's parcel). The only lines in `paste()` that
  changed are the bake branch and the loader branch's switch to `judgedOutcome`.
