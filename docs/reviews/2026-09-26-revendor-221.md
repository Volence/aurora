### STOPPED: a paste into a zone that names music is refused (R3), and the fix is a write-behaviour choice

Measured in the archive copy with aeon's validator: `s2_ehz_cpz` plus a clip written the way `withClip` writes one
(`id, donor, zone, src_rect, dst_rect`; s2disasm EHZ, dst y 2048, no `music`):

```
exit 1  R3 ...: clips 'ehz_act1' and 'ehz_2' are both s2disasm EHZ but name different music ('SONG_S2_EHZ' vs None); a zone's region rows carry ONE song
```

The same clip carrying `"music": "SONG_S2_EHZ"`: exit 0, accepted (with the act's existing W3). So since
`67f7787d`, adding a second clip of a zone already in a music-carrying act is refused, by name, by the validator
the page already calls before writing. **Not a silent break:** nothing is written and the author sees aeon's R3
message. No test or harness row pastes a same-zone clip into s2_ehz_cpz, so the suite is green over it.

Not fixed here because it changes what a paste WRITES (the module's header: "nothing Aurora cannot vouch for").
Options for the owner / a design parcel: (a) `withClip` copies the zone's existing `music` onto a new clip of the
same `(donor, zone)`: the only value R3 accepts, so arguably forced; (b) the paste form shows and sets the zone's
song; (c) leave it refused. A clip of a zone new to the act needs no `music` (absent = no song) and is unaffected.
