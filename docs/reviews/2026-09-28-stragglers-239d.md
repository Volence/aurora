# Row 239 (d): the straggler strokes on whole device pixels

Branch `parcel/stragglers-239d`, from master `2c7921b6`. ROADMAP row 239 (d). Evidence is in
`docs/reviews/239d-stragglers/`. Row 238's packet (`docs/reviews/2026-09-28-device-grid-238.md`,

parity-aware rule: an odd device width centres on a half pixel, an even one on a whole pixel,

## 1. What changed, per site

Every site was re-derived from the current source. The line numbers in row 238's packet had
drifted.

### 1.1 Site 1: the paste ghost (`src/renderer/components/MapViewport.tsx`)

- **On master:** `lineWidth = 2 / pZoom`, dash `[4 / pZoom, 4 / pZoom]`, and `strokeRect` in
  world units under `scale(pZoom) / translate(-vp)`.
- **Now:** the footprint is mapped to CSS px from the camera this block already holds. It is
  stroked by `strokeCssRectOnDeviceGrid(..., 2, dpr)` with the dash set to `[4, 4]`, stated in
  the CSS frame it is now stroked in. That is the same 4 CSS px as before.
- This is the marquee's own treatment (row 238 (a)). It does not read `getTransform()`, for
  the reason row 238 gives: the node suite's map stub must keep answering `undefined`.

### 1.2 Site 2: the collision-paint outlines (`MapViewport.tsx`, `device-grid.ts`)

- **On master:** two INSET strokes. The scope was `1 / zoom` wide, inset by `0.5 / zoom`. The
  primary was `1.5 / zoom` wide, inset by `0.75 / zoom`. So each sat just inside its 16 px
  cell.
- **Now:** a new helper, `strokeCssRectInsetOnDeviceGrid(ctx, cssX, cssY, cssW, cssH,
  cssWidth, dpr)`, keeps the "inside the cell" meaning:
  - each side's OUTER edge is the cell's edge rounded to a whole device pixel;
  - its INNER edge is `deviceStrokeWidth(w, dpr)` device px inside that;
  - each side's centre is asked of `snapStrokeEdges` at a device coordinate that is already
    whole: `floor(w/2)` in from the left or top edge, `ceil(w/2)` in from the right or
    bottom. So the helper's own parity rule puts the centre at exactly `edge ± w/2`.
- The plain centred helper was rejected. Asked at `edge + 0.5`, a 1 px stroke at dpr 1 hits a
  `Math.round` tie on every integer edge and moves one column inward. The inset helper covers
  exactly master's column there. A unit row states this ("at dpr 1 on integer edges the
  scope outline covers the column the world-unit stroke did").
- The shape ghost that `drawCollisionShape` draws inside the cell is NOT in this site. See
  section 6.

### 1.3 Site 3: `OverlayRenderer` (`src/renderer/canvas/OverlayRenderer.ts`)

- `render`, `drawCollisionOverlay` and `drawObjects` take a REQUIRED `dpr`, for classic's row
  194 reason: a default of 1 would be silently wrong. MapViewport passes the `deviceScale()`
  its base transform was built from.
- **Angle marks:** `drawAngleMark` gets `segmentsOnDeviceGrid(ctx, dpr, cameraDeviceMapping(vpX,
  vpY, zoom, dpr))`, the adapter classic has used since row 238 (c).
  - An axis-aligned bar or stem gets both edges whole.
  - A slanted one is drawn where it was.
- **The mapping is stated from the camera.** `segmentsOnDeviceGrid` gains an optional
  `DeviceMapping` argument, and `cameraDeviceMapping` is new in `device-grid.ts`. The first
  attempt read `getTransform()`, and 127 rows of `map-viewport-mounted` /
  `map-device-scale` went red with `Cannot read properties of undefined (reading 'a')`: row
  238's stub problem again. The stub was not changed, and neither was the "CANNOT MEASURE the
  drawing transform" row.
- **The no-preview object box:** `strokeCssRectOnDeviceGrid` at its WORLD width,
  `OBJECT_BOX_STROKE_WIDTH * zoom` CSS px, centred on the box edge as before.
  - **One choice, disclosed.** The width is floored at 0.5 CSS px. Below zoom 0.5 the world
    width is under half a CSS px. The parity rule reads anything that rounds to 0 as EVEN,
    and an even width's minimum is 2 device px, so the faintest border would become the
    heaviest. Half a CSS px rounds to 1, an odd width, so the border is 1 device px (up to
    dpr 2.x). A unit row states both halves.

### 1.4 Site 4: the lenses

- **`drawSectionPriority`, `drawSectionBothPlanes`** (`src/renderer/canvas/priority-lens.ts`,
  `src/renderer/canvas/both-planes-lens.ts`): each takes a required `dpr` and passes
  `drawTileLens` both `dpr` and `toDevice: cameraDeviceMapping(...)`. `TileLensSpec` gains
  `toDevice`, and `drawTileLens` forwards it to the adapter.
- **`drawComposerPriority`** (`src/renderer/canvas/composer-priority-lens.ts`) passes `dpr: 1`,
  and the reason is written beside it.
  - `PixelViewport` sizes the composer's backing store in CSS px (no `devicePixelRatio`) and
    lets the browser upscale the bitmap `pixelated`. So 1 is the scale of the only pixel
    grid a stroke on that canvas can reach.
  - The display's dpr would stroke under a `setTransform(dpr)` that this canvas does not have.
  - On master the 1 px edge was centred ON the tile boundary, half-covering one pixel on each
    side. It now covers one whole backing-store pixel.

### 1.5 Site 5: the legend swatch (`src/renderer/components/CollisionLegend.tsx`)

`AngleSwatch` hands `drawAngleMark` the adapter.

**Finding: this changes no pixel.** The swatch's profile is a `$20` slope, so its bar and stem
are both DIAGONAL, and the rule leaves diagonal segments where they were, at their CSS width.
On screen the swatch is byte-identical to master's: 0 of 324 px differ at dpr 1, and 0 of 729
at 1.5. It is disclosed as a routing, not claimed as a snap. The only row that can go red for

### 4.1 The instrument

`scratchpad/stragglers-239d-harness.mjs` is registered as `npm run harness:stragglers-239d`.

Each run prints the dpr and the canvas rect. Both were 1 and 1.5, forced with
`--force-device-scale-factor`, with the canvas on whole device px:

- dpr 1: rect left 284, top 74, 876 x 721;
- dpr 1.5: rect left 284, top 74, 596 x 522, device origin (426, 111).

The mouse is aimed at integer client pixels.

**How a subject is measured:**

- Two real screenshots are taken, differing only by the state that draws the stroke.
- The device index E is where the ruled rule puts the edge, restated from the parity rule and
  `Math.round`.
- Every sampled pixel of the "on" shot is predicted as the whole-pixel layers composited,
  source-over, onto the same pixel of the "off" shot. The layers are the fills and strokes
  across the edge, with colours parsed from `canvas-colors.ts`. The tolerance is 3 per
  channel.
- A stroke that half-covers a device column matches no whole-pixel prediction.
- The geometry (zoom 2, integer camera, world coordinates on the 8 px grid) keeps every FILL
  edge whole at both dprs, so a fill is never what a row measures.

**The subjects:**

- **p:** paste armed by a real `m` marquee drag, a real Ctrl+C and Ctrl+V, and a real hover.
  The top edge is read inside dash-on runs.
- **c:** the `c` key plus the eraser, then a real hover. The cell's left edge is read.
- **m:** see below.
- **b:** a no-preview object box, found by its own stroke colour.
- **l:** a marked tile with unmarked left neighbours, found from the app's own `ntRect`.
- **bp:** a cell made solid on both planes by an in-memory poke of plane B with plane A's own
  word.
- **lg:** the swatch's pixels, byte-compared with the master build's.

**Finding: the stem subject needs an authored fixture.** Aeon's flat ground carries the odd
"no angle" byte, so it draws no mark. Over 49 cameras across section 0, the app's report
named 482 marks at dpr 1, and every one was slanted. So the harness pokes an air cell, in
memory only, with each bank shape whose angle byte is axis-aligned (read from the copy's
`base/angles.bin`), through `armCollisionBrush`'s own packing, until the app's report names
its mark. The shape was 243, angle byte `0x0`, word `0x30f3`.

One more thing the first try found: the collision legend is a DOM box over the map, and it
grows a row when angles are turned on. The fixture now sits in the view's right half.

## 6. What stays unsnapped, and why

**By the rule's own limits:**

- **Diagonal angle marks** (every slope, on the map and in the legend). A slanted line crosses
  device rows and columns, and no rule is invented for it.
- **Arcs:** the ring circles in `OverlayRenderer.drawRings`.
- **Dash ENDS** along the paste ghost wherever `4 x dpr` is not whole (1.25, 1.35). The dash
  positions stay in CSS px.

**Width ties (finding, not fixed).** The mark's stem core is 2 CSS px, which is 3.0 device px
at dpr 1.5. Its casing is 4.8 CSS px, 6.0 device px at 1.25. Both are exact parity ties.
`deviceStrokeWidth` says "ties go thinner", but floating-point noise in the width's path
(`(k / zoom) * 1.6 * zoom * dpr / dpr`) decides them. Measured through that path:

- the core at dpr 1.5 is 4 device px at zooms 1.5 and 3.625, and 2 at zooms 1 and 2;
- the casing at dpr 1.25 is 5 at 1.5 and 3.625, and 7 at 1 and 2.

Both edges are whole either way. The unit and harness rows accept either same-parity
neighbour at a tie and say which. Classic's marks, through the same adapter, share this. It
is the helper's defect, not this row's.

**The stem sits off-centre in its casing by half a device px.** Row 238's finding (§7.1 there)
now applies to aeon's marks too: the core is even and the casing odd.

**Straggler strokes found and NOT in the five-site list, so not touched:**

- MapViewport's collision-paint SHAPE ghost: `drawCollisionShape` at `lineWidth 1.5 / zoom`,
  `solidEdgeWidth 3 / zoom`, and its own angle mark at `/ zoom` widths.
- `OverlayRenderer`:
  - the collision surface line (`1 / zoom`);
  - the A/B diff outline (`1.5 / zoom`, inset);
  - the tile, block and section grids (0.5, 1 and 2 WORLD px).
- `PixelViewport`'s own chrome on the composer canvas: grid lines, marquee and selection at
  `+ 0.5` on a CSS-sized store.
