## Row 196: GUARD-GATE-CALLS-TRACKED-UNTRACKED

**What it was.** `npm run check:harness-guards` (`scratchpad/check-harness-guards.mjs`) at master printed:

```
UNGUARDED BUT UNTRACKED (1) — present in THIS working tree only.
  Just as able to hijack another Aurora; not fatal because the repo does not carry them.
  Committing one makes it a hard failure.
  G9 scratchpad/preset-schema-key-probe.mjs: registered as `harness:preset-schema-key` but never prints PASS, ...
════ 295 clean / 296 classified (285 .mjs + 11 .sh) · 0 failure(s) · 1 unguarded-untracked · 0 unmeasurable ════
exit=0
```

(The brief's "7 unguarded-untracked" was measured in the owner's checkout, where six more untracked
scratch files exist. A worktree has only the tracked one.) `git ls-files --error-unmatch
scratchpad/preset-schema-key-probe.mjs` names the file, while the same command on a nonexistent path
exits 1. The file was committed at `423f3bb3` and registered at `2a8d71cd` (2026-09-12). The row was
still true.

**Cause.** Every other rule keys its failure by the scratchpad-relative path. G9 keyed it as
`scratchpad/<file>`. The tracked/untracked split compares keys against `git ls-files scratchpad` with
the prefix stripped, so no G9 key could ever match: **every** G9 failure was filed untracked and
non-fatal. G6 carries a comment warning of exactly this spelling, and G9 was written without it.

**Should a tracked G9 violator fail the gate?** I decided this from the gate's own header, so it was
not a design call of mine: "tracked failures fail the build; untracked ones are reported loudly and
do not", and the heading itself says "Committing one makes it a hard failure". G9 is described as a
ratchet. The fix makes the gate do what its header already says.

**Change** (`5e164707`, `scratchpad/check-harness-guards.mjs`):
1. The split normalises the key once (`[GS]\d+ ` prefix and an optional `scratchpad/` stripped),
   instead of trusting each rule's spelling.
2. "Untracked" is now a positive finding rather than a fallback. A failure goes there only when its
   key names a file this run walked and git does not carry. A key naming neither goes under a new
   fatal heading, "FAILING, AND THE TRACKED/UNTRACKED SPLIT CANNOT PLACE THEM", and counts as a
   failure. So the next rule that uses a new spelling goes red instead of quietly non-fatal.

With the fix, the gate correctly failed on the probe. The probe is a real gate: 29 rows, `exit 1` on
any FAIL row. It printed `ok` for a pass, and G9 greps for `PASS`. It now prints `PASS`, and all 29
rows print PASS / ALL ROWS HELD, exit 0. Gate: `296 clean / 296 classified · 0 failure(s)`, exit 0.

**Proofs** (each run on a committed baseline; each mutation shown on disk; restored with
`git checkout HEAD --`):

- **My first M1 stayed GREEN, and that exposed a flaw in my own change.** The mutation reverted the
  probe's printer to `ok`. My new comment above the printer contained the word `PASS`, and G9 is a
  source grep, so the comment satisfied it. I restored from HEAD, reworded the comment so it describes
  the word without spelling it, and committed that (`a9729d8c`). I then re-ran M1:
  ```
  -  console.log(`${ok ? 'PASS' : 'FAIL'} ${label}${detail ? `\n       ${detail}` : ''}`);
  +  console.log(`${ok ? 'ok  ' : 'FAIL'} ${label}${detail ? `\n       ${detail}` : ''}`);
  ```
  exit=1, `FAILING (1): G9 scratchpad/preset-schema-key-probe.mjs: ...`. Master's gate on the same
  printer exited 0 with the file under UNTRACKED (the baseline run above).
- **M2**, M1 plus the normalisation removed:
  ```
  -  const keyOf = (f) => String(f).replace(/^\s*[GS]\d+ /, '').split(':')[0].replace(/^scratchpad\//, '');
  +  const keyOf = (f) => String(f).replace(/^\s*[GS]\d+ /, '').split(':')[0];
  ```
  exit=1, listed under `FAILING, AND THE TRACKED/UNTRACKED SPLIT CANNOT PLACE THEM (1)`. The backstop

  zz-plant-untracked.mjs`. The heading is still used, and only for untracked files.

**Change** (`ae83c254`). New `src/renderer/state/__tests__/helpers/sync-effect-site.ts` parses

- **[F2]** now claims only that the re-sync exists and every call sits in a `useEffect` callback

- **[K0]** claims that those deps resolve, through `const` bindings, to a call of the key function
  whose first argument resolves to the history-clock hook and whose second resolves to the art
  store's read of the open-document field.

All names come from the source. Export names are looked up by identity in the modules the component
imports (`chunk-doc-commit`, `hooks/useHistoryVersion`, `artStore`). Imports are matched by resolved
path, so an alias is followed. The field name is typed `keyof` the store's state, so typecheck
refuses it on a rename. The read is loud when it cannot measure: a missing import, a name declared
twice, or zero call sites is reported as `unmeasurable`, and both rows fail on it. It is still a
source read: it proves the wiring, not that React runs the effect (`harness:chunk-links` row 9 does
that, and it is not in `npm test`).
