## 1. (a) The even-width chrome

### 1.1 Callers, re-derived

`grep 'snapStroke('` over `src/`, excluding tests and `device-grid.ts`, found 3 files, and the
census's line numbers had drifted by one or two. Every call site, with the CSS width it passes:

| File | Site | Width | Device width at every dpr |
|---|---|---|---|
| `screen-frame.ts` | frame rect (x, y, lineWidth) | 1, or **2 when active** | odd / **even** |
| `effects-guides.ts` | `plane_y` rule, casing | 3 | odd |
| `effects-guides.ts` | `plane_y` rule, line and row | 1 | odd |
| `effects-guides.ts` | layer guide | 1, or **2 when hovered, dragged or refused** | odd / **even** |
| `region-overlay.ts` | unassigned hole outline, the hatch's lineWidth, trimmed outline | 1 | odd |
| `region-overlay.ts` | region union outline | 1, or **2 when selected** | odd / **even** |
| `region-overlay.ts` | dragged rect | **2** | **even** |

The brief left moving the odd-width callers optional ("leave them unless moving them is
byte-identical"). **I moved them all**, because for an odd width `snapStrokeEdges` returns
exactly `snapStroke`'s answer. The goldens prove it: 0 odd-width calls moved (1.3). With every
call site moved, a census row can then lock the defect class (1.4).

**One choice, disclosed.** The guide's label and the frame's caption used to be positioned from
the stroke's centre. I kept them anchored on the 1 px line's centre
(`snapStrokeEdges(v, 1, dpr).at`). Otherwise hovering a guide or the frame would move its label
by half a device pixel. As a result, no label call moved in either golden.

### 1.2 Measured on master first, on screen

`scratchpad/even-chrome-239-harness.mjs` is new and registered as `harness:even-chrome-239`.
For each launch (`--force-device-scale-factor` 1 and 1.5) it produces four subjects, each by real
CDP input on an aeon COPY:

- **g:** a guide, hovered by a real mouse move.
- **f:** the frame, made active by a real hover on its right edge. The right and bottom edges are
  read, because the frame's left and top edges sit on the canvas edge.
- **r:** a region's outline, selected by a real click on its panel row.
- **d:** the dragged region rect, from a real press and move with the tint hidden. The mouse is
  released at the press point, and the document is checked to be as seeded.

The instrument:

- It takes two real screenshots, before and after the state change.
- E is the device index `snapStrokeEdges` centres the even stroke on (canvas device origin plus
  `round(edge x dpr)`).
- It reads E-3..E+3 over about 60 sampled lines. The sampled lines skip labels, the other guide
  and the frame corners.
- Colours are parsed from `canvas-colors.ts`.

The rows are:

- **.2:** E-1 is the opaque stroke colour.

### 1.3 The goldens: which entries moved

The brief named one golden (`dpr-chrome.test.ts`). **The files name two.** Row 208's
`region-overlay-middrag.test.ts` compares every `drawRegionOverlay` call against
`region-overlay-full-master.golden.json`, and three of its cases draw a selected region. The
ruling ("re-record the golden with the reason") covers both, so both were re-recorded.

**The mechanism.** Neither test has a regen switch. Each golden was written by a one-off vitest
spec that was deleted after it ran:

- the chrome golden's generator is quoted at
  `docs/captures/2026-09-12-dpr-guides-offset/dpr1-golden-generator.ts.txt`;
- the region golden's generator is described in `2026-09-25-regions-middrag-preview.md` §3.

I wrote one spec in their shape (`239-even-chrome/golden-generator.ts.txt`: same recorder, same
scenarios, same file format). **Fidelity check:** run on the pre-239 sources, it reproduced BOTH
old files byte for byte except `generatedFrom`. Then it ran on the fix, and the spec was deleted.

**What moved.** `golden-moved-entries.py` walks old and new in step. For each call it finds the
device width it is drawn at: the width in force at a `strokeRect`, or at the `stroke()` that draws
a `moveTo`/`lineTo`. An earlier version read the width at the moveTo and reported NOT ONLY for
the guides, because `effects-guides.ts` sets `lineWidth` after building the path. That is how
the script was seen to fail.

| Golden | Case | Calls moved | What |
|---|---|---|---|
| dpr1-chrome | guides: screen space, hover on 1, refusal on 2 | 4 | `moveTo/lineTo y 200.5 -> 200`, `221.5 -> 221`, width 2 |
| dpr1-chrome | guides: a drag in flight on 0 | 2 | `31.5 -> 31`, width 2 |
| dpr1-chrome | frame: active, zoom 2.5 | 1 | `strokeRect [60.5, 80.5, 800, 560] -> [60, 80, 800, 560]`, width 2 |
| dpr1-chrome | the other 9 cases (1 px guides, `plane_y` 1 and 3 px, frames at rest, camera, lens) | 0 | |
| region-overlay | at rest, west selected | 8 | west's 4 outline segments, `x.5 -> x`, width 2 |
| region-overlay | mid-drag, west selected (dpr 1) | 16 | |
| region-overlay | mid-drag, dpr 1.35 | 16 | |
| region-overlay | nothing selected; a hole where south was | 0 | |

Both verdicts (`golden-moved-dpr1-chrome.txt`, `golden-moved-region-overlay.txt`): every moved
call is `moveTo`/`lineTo`/`strokeRect` under an EVEN device `lineWidth`. Op sequence, call

**What the goldens guarded is still guarded.** Every other call is still master
