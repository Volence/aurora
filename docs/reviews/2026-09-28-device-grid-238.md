## 1. (a) MapViewport's own stamp ghost and marquee

### 1.1 Re-measured on master

In `drawCollisionPreview` at `3ca6cda2`, both outlines were still stroked in world units
under `setTransform(dpr) / scale(zoom) / translate(-vp)`, with `lineWidth = 2 / zoom`,
and the marquee dashed at `4 / zoom`. So at 1.5 each is 3 device px wide, centred wherever
the world edge falls. The finding holds.

### 1.2 The fix

- `strokeRectOnDeviceGrid` moved from `classic-overlays.ts` into `canvas/device-grid.ts`,
  with no change to its behaviour. `classic-overlays.ts` re-exports it, so row 237's
  imports and tests are unchanged.
- The new `strokeCssRectOnDeviceGrid(ctx, cssX, cssY, cssW, cssH, cssWidth, dpr)` is the
  same snap for a rect the caller already has in CSS px. `strokeRectOnDeviceGrid` is now
  that function plus a `getTransform()` read.
- MapViewport maps each rect to CSS from the camera it already holds, `(x - vp) * zoom`,
  and strokes it through `strokeCssRectOnDeviceGrid` at 2 CSS px.
  - The marquee's dash is `[4, 4]` in the CSS frame it is now stroked in. That is the
    4 CSS px it always was.
  - The fill and the ghost art are unchanged, because they are fills and images, not
    strokes.
- **Why the CSS variant exists** (`9e1d78d3`). The first version (`0f55b8cc`) called
  `strokeRectOnDeviceGrid` from MapViewport. The full suite then went red on 27 rows of
  `map-viewport-mounted.test.ts`, with `TypeError: Cannot read properties of undefined (reading 'a')`:
  - the node suite's shared stub context answers `getTransform()` with `undefined`;
  - `map-device-scale.test.ts` has a row that REQUIRES it to stay unanswered ("CANNOT
    MEASURE the drawing transform").
  So MapViewport now maps the rect itself instead of reading the transform. The stub was
  not changed, and neither was that row.

## 2. (b) `CollisionLegend` and `AnchorSweepPreview`

### 2.1 Re-measured on master

Both own a dpr-sized store, and neither subscribed. One correction to row 237's packet:
neither read `deviceScale()`. Both read `window.devicePixelRatio || 1`, once, inside an
effect keyed on something else.

- The legend's `AngleSwatch` keyed its effect on the zoom.
- `AnchorSweepPreview` keyed its effect on the play state.

### 2.2 The fix

- **`AngleSwatch`**, now a named export so it can be mounted in the node suite. Its paint
  is one function. The effect calls it once and returns `onDeviceScaleChange(paint)`.
- **`AnchorSweepPreview`.** The sizing is one function (store plus `setTransform`),
  subscribed with `onDeviceScaleChange`, and the unsubscribe is in the effect's cleanup.
  The rAF loop's next frame repaints into the new store. While the window is hidden no
  frames run, and the loop resumes on `visibilitychange` as before.
- Both now read the scale through `deviceScale()`, the map surfaces' rule, so the listener
  and the store agree on what an unusable reading means. This differs from master only for
  a NaN, Infinity, negative or non-number `devicePixelRatio`. Master's `|| 1` let a
  negative or Infinity reading through.

## 3. (c) Classic's object, start, priority and loop-glyph strokes, and the angle mark

### 3.1 Re-measured on master, item by item

| stroke | on master | now |
|---|---|---|

| ghost-marker (invisible object) box | raw dashed `strokeRect` | `strokeRectOnDeviceGrid`, 1 CSS px; dash `[3, 2]` CSS px (the 3/2 it always was) |
| selection box | raw `strokeRect`, 2 CSS px | `strokeRectOnDeviceGrid`, 2 CSS px (even width: half-covered edges, by the rule) |
| start marker crosshair | raw path, 2 CSS px | `segmentsOnDeviceGrid` (below), 2 CSS px (even width, as above) |
| start marker ring | `arc` | **unchanged.** A circle has no whole-pixel answer under the rule |
| ring-object circles (no sprite) | `arc` | **unchanged**, same reason |
| priority lens edges | `drawTileLens`, 1 CSS px in world units | `drawTileLens` with the new optional `dpr`, through `segmentsOnDeviceGrid` |
| loop glyph | **no stroke at all**: a filled disc and a `∞` glyph (`drawLoopGlyph`) | nothing to snap. **This item did not hold**, and a census row locks it |
| angle mark | `drawAngleMark` in world units | axis-aligned bar and stem snap; diagonal ones are drawn where they were (below) |

### 3.2 The fix

**`segmentsOnDeviceGrid(ctx, dpr)`**, in `canvas/device-grid.ts`, is new and has the shape
of `MarkDrawCtx`. It is a path context in the caller's world units.

- It maps each straight segment to CSS through the transform in force, and strokes it
  under `setTransform(dpr)`.
- For a HORIZONTAL segment, the row goes on `snapStroke(y, w).at`. For a VERTICAL segment,
  the column goes on `snapStroke(x, w).at`. In both cases the ends go on `snapLength` and
  the width is `deviceStrokeWidth(w, dpr)`. This is the same rule
  `strokeRectOnDeviceGrid` and 237's surface line use.
- A DIAGONAL segment is drawn where it was, at its unsnapped CSS width. The rule is about
  device rows and columns, a slanted line crosses both, and no rule for it is invented.
- "Horizontal" means the other axis moves less than 1e-6 CSS px. The reason is that
  `angleNeedle` builds directions from `Math.cos`/`Math.sin`, and a quarter turn leaves
  about 6e-17 rather than zero. A row holds this.
- It draws one path per width, so the lens's many edges are still one stroke.

**The call sites:**

- `drawTileLens` takes an optional `dpr`. When it is given, the edges go through the
  adapter. Aeon's three lens callers pass nothing, so their picture is unchanged. The
  dpr-1 identity hash in §4 covers the map canvas.
- `drawPriority`, `drawObjects` and `drawStart` take a REQUIRED `dpr`, for the reason
  `drawCollision` gave at row 194: a default of 1 would be silently wrong. For
  `drawObjects` the parameter is inserted after `invZoom`.
- `drawCollision` hands `drawAngleMark` the adapter in place of `ctx`. The shared
  `drawAngleMark` in `core/` is untouched. Its other callers (aeon's `OverlayRenderer`
  and the legend swatch) still draw unsnapped. See Open.

## 6. Open

- **RULING WANTED: at dpr 1, MapViewport's ghost and marquee edges got softer.**
  - Master stroked them at `2 / zoom` in world units. At an integer camera and zoom, that
    covered **two whole device columns**, which is crisp (m.s1 on master: C-1 and C both
    full).
  - The ruled rule centres a 2 px line on a device half-pixel. So at dpr 1 it is now half,
    full, half (m.s1 on the fix: C-1 and C+1 partial).

    four columns, two of them half-covered, and the rule's 2 device px is consistent and
    thinner.
  - The docblock in `canvas/device-grid.ts` says a 2 px line "keeps the half-covered edges
    it has always had at dpr 1". That is true of the chrome it was written for, which was
    already drawn at `round(v) + 0.5`. It is NOT true of these two outlines, nor of the
    classic stamp-drag preview row 237 snapped the same way.
  - This parcel followed the ruling and did not invent a rule (for example, an even width
    on a whole-pixel centre). Whether 2 px strokes should keep crisp dpr-1 edges is the
    overseer's (or the owner's) call.
