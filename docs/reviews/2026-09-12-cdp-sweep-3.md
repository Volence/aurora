## 5. Findings and observations

No defect in the three fixes. Stated as observed, with no fix attempted:

1. **O1. After a successful switch the shell leaves Home.** S1a to S1b: the Green Hill tab stays
   listed, the act drops (`open/loading/ghz1`) and reloads from S1b, and Home is no longer the
   active pane (its header box read 0x0 until the Home tab was pressed). S1b to aeon: the tabs read
   `["Home","Oracle Jungle Zone · act1"]` and Home was not the active pane either. The packet's
   F-4 says only "the successes still switch", which holds. Whether leaving Home is intended is not
   judged here.
2. **O2 (harness, this repo's rigs).** `Page.captureScreenshot` with a non-positive clip never
   answers, so a rig without a per-call deadline hangs silently. Run 0 hung ten minutes on it.
3. **O3 (harness).** Electron has no `Browser.getWindowForTarget`; `window.resizeTo` does resize
   the window under Xvfb.

**5.2 Where the tree and my rows disagreed.** Run 2's CFO.F4.a asserted "the act is dropped" as an
end state after a successful switch. The packet never says that; the shell reopens the same tab id
(`level:ghz:1`) in the new project. The same observation showed that F-1's "the act is still
loaded" could be vacuous, since dropped-and-reloaded reads the same afterwards. So every typed open
now runs an in-page 4 ms sampler. F-1, F-3 and F-2 require it never to leave `open/ready`, and
F-4.a requires it to show the drop, so the sampler is known to see one. The red run in 3.1 is the
proof that the steady rows can fail: there the trace read `opening/idle > closed/idle`.
