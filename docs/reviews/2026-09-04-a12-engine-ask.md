## 1. The ask, in one paragraph

In the **DEBUG shape only**, let `Effects_InstallPreset` take its `EffectsPreset*` from a
**46-byte RAM shadow** when a trigger word is set, instead of from the section's
`sec_effects` — and clear the trigger on the way out. Aurora writes both the shadow and
the trigger over the Aether bus. That is the whole engine half of the live effects
preview.

## 2. Why it is this small: three quarters of it is already built

I went looking for what a live preview would need and found aeon has most of it.

- **`Effects_InstallPreset (a0: u32)`** (`engine/effects/preset.emp:279`) is TOTAL
  BINDING — it writes every channel from the preset `a0`'s section names, then latches
  world lines. Its own header says it *"runs from the MAIN LOOP (the crossing site)"*
  (`:293`). The crossing site is `engine/level/parallax.emp:1115`,
  `jbsr Effects_InstallPreset  // a0 = Sec* in, a0 = resolved parallax config out`.
- **`EffectsPreset` is 46 bytes, flat, and has no variable-length parts**
  (`engine/effects/preset.emp:66-88`, `pub struct EffectsPreset (size: 46)`): five
  `*u8`, one `[*u8; 2]`, `[u16; RASTER_MAX_PATCH] ep_patch_world_ys`, `u16
  ep_transition`, `[u16; RASTER_MAX_PATCH] ep_patch_motion`. That struct comment records
  the size being **declared wrong twice** — 36 while it was 32, for two tasks, because
  nothing in the `use` closure evaluated the `ensure` — so I checked it against the
  offsets and the constant rather than the prose: `RASTER_MAX_PATCH = 4`
  (`engine/effects/raster_dsl.emp:2131`), so `ep_patch_motion @ $26` + 8 = 46. **46 is
  right.** See §5 for the half of that check that is Aurora's.
- **An arbitrary preset already gets installed mid-play, on demand, from a debug path.**
  `Debug_PresetCycleHotkey` (`games/sonic4/test/ojz_scroll_test.emp:2630`, START held +
  A pressed) walks a cursor over the act's sections, resolves the `Sec*`, stands down on
  a null `sec_effects`, calls `Effects_InstallPreset`, then `Parallax_StartTransition`,
  then repaints a readout. It is guarded by `Input_Source` being live and is edge
  triggered.

So the install, the safety gate, the transition and the readout all exist and are
exercised. **What does not exist is a preset the editor can write, and a way to fire the
install from something other than a gamepad.**

## 3. The two gaps, stated as the two things I am asking for

**(a) A RAM `EffectsPreset` Aurora can poke.** Everything the lab installs today lives in
ROM. A shadow in DEBUG RAM (`Debug_Effects_Shadow`, sized by `sizeof(EffectsPreset)` —
please derive it, do not spell a literal) is the missing storage.

**(b) A bus-reachable trigger.** `Debug_PresetCycleHotkey`'s trigger is START+A. Aurora
cannot press it. A one-word cell (`Debug_Effects_Shadow_Arm`) that the same main-loop
poll consumes and clears would do: Aurora writes the 46 bytes, then writes the arm word,
and the next frame installs. Consuming-and-clearing is what makes it a one-shot rather
than a per-frame reinstall, which matters because the install is not free and runs in
the crossing hot path.

Both are yours to shape. I am naming the seam, not the implementation.

## 4. ⚠ The scope boundary, stated up front because it decides whether this is worth your time

**Six of the preset's fields are POINTERS** (`ep_pal`, `ep_parallax`, `ep_raster`,
`ep_patched`, `ep_cycle`, and the two `ep_variants` slots). A RAM shadow therefore makes
live:

- **the inline words** — `ep_patch_world_ys[8]`, `ep_patch_motion[8]`, `ep_transition`.
  That is exactly the surface Aurora already ships controls for (`BandPresetPanel.tsx`:
  World Y, Movement, Travel, Cycle, Start at), so a slider would move a boundary on
  screen at frame rate with no build; and
- **which already-built ROM blob each channel points at** — swapping among programs,
  palettes and cycles the ROM already contains.

It does **not** make new blob *content* live. A band program that does not exist in the
ROM, a new palette, new tile art — all still need a build. **I am not asking you to
change that**, and I am not asking whether those pointers could aim at Aurora-written RAM
buffers instead: that is a question about whether the palette/raster installers carry ROM
assumptions (DMA source, alignment, bank), which is yours to answer and not mine to
assume. If the answer is "they could", it is a second, larger ask and I will file it
separately.

**So the honest value line: this buys live anchor and sweep authoring, plus live
swapping among what is already built. It does not buy live art.** If that is not worth
the DEBUG RAM to you, say so and I will close the row rather than leave it open against
you.

## 5. The channel count, checked on both sides rather than assumed to match

The shadow's size turns entirely on the patch-channel width, and the two repos hold that
number independently, so I measured both rather than trusting the pair to agree:

| | value | where |
|---|---|---|
| aeon | `RASTER_MAX_PATCH = 4` | `engine/effects/raster_dsl.emp:2131`, with `scene_dsl.emp:56` holding an `ensure` against drift |
| contract | `maxItems: 4` on both `patch_world_ys` and `patch_motion` | `aurora-effects-preset.schema.json` |
| aurora | `EFFECTS_PRESET_MAX_PATCH` | derived from the schema, not spelled — `effects-preset.ts:2373`, `:2544` |

**They agree, and Aurora's is derived rather than copied**, so it cannot drift on its own.
This is stated because if it had been 8, the shadow would be 54 bytes and every number in
§2 would be wrong; a size that happens to be right is not the same as one that was checked.

## 6. What Aurora does once this lands

`A12` on aurora's board: the write-path half — pack the 46 bytes from the open preset,
write them plus the arm word over the existing Aether client, debounce, and drive it from
the controls that already exist. Nothing in it is blocked on anything but this ask.
