## 2. The recurring causes, which are worth more than the individual fixes

### 2.1 One commit, `598be067`, hit FOUR files

`598be067` ("fix(ui): the §5 accessibility and consistency calls", 2026-08-16)
made every **interactive** `Chip` a real `<button>` where it had been a `<span>`.
Four instruments in this parcel read chips with a `<span>`-only scan:
`paint-through`, `tile-editor`, `capture`, `shell-flip`.

The damage is not that the rows went red. It is **what a broken reader returns**:
`chipEnabled('Undo')` answered `null` and `chipCount('FG')` answered `0` — which
is exactly what a **deleted control** answers. "I looked and the control is
disabled", "I looked and there is no such control", and "I could not look" all
printed the same value. In `paint-through` that produced a **false GREEN**: a
`drain()` that pressed nothing returned 0, later checks then ran on an act nobody
had reset, and `[3]` passed on a cell that was already off the shared block.

The same commit hit this parcel a **fifth** time in its other form — not the
element type but the **value**. `canvas-cdp` `[11c]`/`[11m]` pinned the New
Canvas dialog's `128x128` default, which `598be067` moved to `256x256`
deliberately (256 is one chunk, the smallest a commit can take; at 128
`canvasChunkCapacity` floored to zero).

Every repair now reads the app's own declaration and **REFUSES by name** when it
cannot, so unmeasurable can never again render as 0, as `null`, or as absent.

### 2.2 Frozen pins that assert the ABSENCE of shipped features

Four files (`s1-sonic-sprite`, `capture`, `shell-flip`, `canvas-cdp`) carried
rows whose comments said, in effect, *"and this must not exist"* — about things
the product then shipped on purpose:

- the sonani dialect "stays unparsed — no fake anims" (un-excluded at `72921f62`,
  2026-08-21; the row had been red for thirteen days);
- `['Layout','Art','Objects','Palette']` and a row literally named "NO Collision
  pill" (collision joined `S1_FACETS` at Stage 3b, 2026-08-17; art moved last
  2026-08-14);
- place-object on the Layout dock (it left `facetTools.layout` 2026-08-14);
- "exactly s1's FOUR overlays" (s1 declares seven); "aeon still shows its six
  pills" (aeon grants seven);
- the `128x128` new-canvas default (`598be067`).

A pin like this is not merely stale — it is **an instrument arguing against the
roadmap**. Every one now derives its expectation from the declaration the app
itself renders from (`S1_FACETS`, aeon's `facets:` grant, `BUILTIN_FACETS`,
`facetTools.layout`, `TOOL_IDS`, `TOOL_LABELS`, `OVERLAY_KEYS_BY_ENGINE.s1`,
`NEW_CANVAS_DEFAULTS`), so the next deliberate change moves the instrument with
it instead of against it.

### 2.3 Shared global state decided results — in four different files

Nothing in this population owns its own state, and it shows:

- **a trailing slash on `AEON_DIR`.** `addRecentProject` normalises the path and
  `HomeTab` renders `title={r.path}`, so a selector built from `AEONDIR + '/'`
  hunts a title the app cannot render. It killed `tile-editor`'s `[18]` and
  **the whole aeon phase** of `shell-flip`, which `return`ed the moment the
  recents card was missing — five rows that had never run in this population.
  O53 §5 named three sites for this; these were the last two unfixed.
- **an unseeded ten-entry recents LRU.** `~/.config/<app>/recent-projects.json`
  is one file every project-opening harness rewrites. Measured 2026-09-03, it
  held **eight other agents' throwaway aeon copies** and not the resolved one, so
  whether a row could run depended on which instrument had run last — and the
  miss was reported as a FAIL reading "COULD NOT TEST", which looks like a
  product failure.
- **a persisted facet nobody reset or asserted.** `tool-split` and `shell-flip`
  both had runs that inherited a facet from whatever ran before (Collision;
  Palette) and went on describing their failures as if they were on Layout —
  eight rows in `shell-flip` about a facet nobody selected.
- **one shared Chromium profile**, which is §4 and is the largest of them.

### 2.4 A `kill('SIGKILL')` that reaped one process and hung three runs

Three of the eight (`tool-split`, `capture`, `shell-flip`) hung and were killed
at the sweep's 600 s cap, so their tallies were recorded as **lower bounds**.
The cause is one line: `el.kill('SIGKILL')` signalled a single process, while
Electron's children inherit the stdio pipes — so node's event loop never drained
and the run hung *after* printing its summary. `killTree` was **imported and
unused** in every one of them. All three call it now, and none hangs.

### 3.2 `[11c]`/`[11m]` — STALE INSTRUMENT

The frozen `128x128` pin of §2.2. Both rows now read `NEW_CANVAS_DEFAULTS` out of
`src/renderer/shell/new-canvas.ts` and refuse if it cannot be parsed; `256` is
never typed, and the row title prints the value it derived.

### 3.3 The other seven — the shared Chromium profile, reproduced exactly

All seven read what the **previous session** left in `localStorage` under
`aurora.session.v1:<project dir>` (this harness is four sequential Electron
launches, not one). If that key is absent the app has nothing to restore *from*,
and every one of them fails **in the wording of a product failure** — "the canvas
TAB does not survive a restart".

Three facts make that the likely condition during the sweep, and the third is a
reproduction rather than an argument:

1. `~/.config/<app>/Local Storage` is **one directory** shared by this entire
   instrument population — the same shape as O52's recents-LRU finding, one layer
   down.
2. **114 call sites** in `scratchpad/*.mjs` call `localStorage.clear()`.
3. The sweep **cannot have run its 89 launches serially** in the window it
   records: it reports 04:02:29Z→04:54:31Z for static analysis *and* the run
   stage, and this file alone takes ~190 s. Its recorded 1-minute load of 14.28
   corroborates. (The sweep document does not state whether it parallelised; this
   is derived from its own figures, and it is derivation, not testimony.)

**The reproduction.** A single `localStorage.clear()` injected between session A
and session B, on the **committed** instrument:

```
checks: 45, fails: 9
  [11c] [11m] [13a-tab] [13a-focus] [13a-pixels] [13b-pane] [13c] [13d] [14a]
```

**36 passed / 9 failed — the sweep's tally to the row, and the same nine ids in
the same order.** The per-session decomposition matches too: A 35 P / 2 F
(identical to my clean run), B 0/3, C 1/3, D 0/1-then-truncated.

`waitRestored` now asserts that key **before any row is allowed to judge the
app** and refuses naming the mechanism. Under the same injected clear the run
reports **zero failures against the app** and one named refusal.

### 3.4 The silent truncation that hid seven MORE rows

`sessionD` bailed on a bare `if (!st) return;` the moment `[14a]` could not read
the document — dropping `14a2 14b 14c 14d 14e 14f 14g` with **nothing said**.

That is why the sweep's arithmetic looked whole: 36 + 9 = **45**, and this file
has **52** rows. The seven are the difference. Nothing in the output
distinguished "seven rows passed" from "seven rows were never attempted".

There is now an `unexercised()` reporter beside `check()`/`neg()`: rows that
could not be attempted are printed by id with the reason, counted separately in
the summary (`checks: N, fails: N, unexercised: N`), and set a non-zero exit. A
row that was never asked is an absence, not a pass.

### 3.5 ⚠ A second cause the new guard found by tripping on its own

The guard tripped **spontaneously** — no poison, load ~3, nothing else running —
at session C, then at session D, then at session B on later runs. The teardown's
`window.close()` does not reliably get the localStorage area to disk.

**Measured, 4 trips in 9 guarded runs (~44%).** The next session boots to
`keys present: ["aurora.session.v1:no-project"]` — the fresh boot's own key
written, the previous session's gone.

Two fixes were attempted and **neither worked**, both recorded so they are not
re-tried:

- The fixed `sleep(4000)` after `window.close()` was replaced with a bounded wait
  for the actual process exit, which **printed the diagnosis**: the app is fully
  gone **~99 ms** after `window.close()`. The 4 s was time spent watching a dead
  process, which is why nobody could have fixed this by lengthening it. The
  bounded wait is kept because it prints which way the teardown went.
- A 6 s settle *before* the close, on the throttled-commit theory. **1 trip in
  2 runs** — no better. It is a comment in the file, not code.

**THE FLAKE IS NOT FIXED AND IS NOT CLAIMED FIXED.** §6 carries it as open. What
*is* fixed is that it can no longer be mistaken for the app losing a canvas tab:
before this parcel it produced app-defect FAILs on the restart rows, which is
almost certainly a second contributor to the sweep's seven.

### 3.6 Two hypotheses tested and thrown away

Recorded because a triage that only reports its successes is not a measurement:

- **A lost race on the restore settle.** `waitRestored` ends in a fixed
  `sleep(3000)`; the sweep ran at load 14.28. Shortening it 10× to 300 ms:
  `checks: 52, fails: 2` — **all seven restore rows still green.** Refuted.
- **Self-pollution across runs.** `main()` deletes `CANVAS_DIR` but never clears
  `localStorage`, so a second run inherits a stored session naming canvases whose
  files were just deleted. The second run was green. Refuted.

### 3.7 One hardening that is NOT proven, said plainly

`firstSessionPayload` took the **first** stored-session key that was not
`no-project`, whichever project it named — so on this shared profile
`[13a-focus]` could compare another project's `activeId` against this run's
canvas tab and report a focus the app never held. It is keyed on the project
directory now (`sessionPayloadFor`).

**This one has no poison behind it.** It is reasoned from reading the code, it is
low-risk, and it is not counted among the three proven repairs. Stated here
rather than folded into the tally.

## 5. ⚠ THE DISAGREEMENT — `shell-flip`'s baseline, unresolved

**This is stated as a disagreement because it is one, and it is not resolved.**

`shell-flip-harness` measured its own pre-repair baseline at **18/38**. The sweep
recorded **21/38** on the same rows. The dead session **did not reproduce the
sweep's number and did not isolate which three rows differ**, and did not claim
to.

**The likely cause is a hypothesis, not a finding.** Both mechanisms that make
that file's result depend on what ran before it were found in it: the
**persisted facet** (§2.3 — a run that inherited Palette described eight rows'
failures as if it were on Layout) and the **shared recents LRU** (§2.3 — which
held eight other agents' aeon copies). Either would move a tally between runs
without moving any code.

**What this parcel adds to it, and what it does not.** §3.3 demonstrates — with
a reproduction, not an argument — that shared per-user state *can* move a file's
tally by exactly the amount that looks like an app defect, on a neighbouring
instrument, in this same population. That raises the prior on the hypothesis. It
is **not** evidence about `shell-flip`'s three rows, which remain unidentified.
Both runs are also lower bounds on the sweep's side: the sweep's `shell-flip`
run **hung and was killed at the 600 s cap**, so 21/38 is a number taken from an
incomplete run.

**Open. Not carried as resolved anywhere.** The cheap next step, if it is ever
worth the time: re-run `shell-flip` at the sweep's revision with the profile and
the recents file snapshotted and restored per run, and diff the row ids.

## 8. ⚠ A hazard found while setting up, and NOT fixed here

`canvas-cdp-harness.mjs` `main()` opens with
`rmSync(CANVAS_DIR, { recursive: true, force: true })`, where
`CANVAS_DIR = ${S1DIR}/.aurora/canvas`.

**Run with `S1DISASM_DIR` unset or pointed at the live tree, this instrument
DELETES the owner's canvas art.** The live `s1disasm/.aurora/canvas/` holds 20
files as this is written (`commit-a`, `test`, and eight `sectioncol*` pairs from
2026-08-16→22). Every run in this parcel used a throwaway copy and the live tree
is untouched.

It is left as-is because guarding it properly is a change to the fixture policy
this parcel does not own — the same ruling shape as the peer-tree policy in
`docs/reviews/2026-09-03-o50-triage-bganim.md` §C. It is flagged here so the next
run of this file is not the one that discovers it.
