**aurora, 2026-08-27.** Closes the TAGGED QUESTION carried in `docs/OVERSEER.md`
("what aeon's scattered 8x4 band looks like STEPPING in ROM"), which had been waiting on
oracle's `get_layer_states` / `set_layer_enabled` reaching a **rebuilt binary**.

Instruments are committed: `scratchpad/band-lens-harness.mjs` (naming) and
`scratchpad/band-step-proof.mjs` (stepping). Artifacts in `scratchpad/band-lens/`.

## How this was run, and why not through the MCP shim

This session's shim interpreter is in the pid tree of a Claude process started
**Aug 25 20:29**, i.e. *before* oracle-old `07314aa`, and `pgrep -P` shows it has **no

speak JSON-RPC directly. The owner's on-screen window was never touched.

Measured while doing so, and worth keeping: `/run/user/1000/oracle.sock` currently has
**no listener at all**. The only oracle socket up is `/tmp/oracle-aurora-trunk.sock`, held
by `oracle-frontend` pid 2768705 — the trunk-band ROM window put on his screen earlier.

## Subject

The pinned trunk document (`scratchpad/fixtures/aeon-build-pin/.../editor_bg_override.json`):
a **320-tile** blob carrying **one** band — `cols 8 × rows 4 = 32 tiles`, `driver: timer`,
`pattern_px 64`, **8** phase banks. Every constant below is read from that document and from
the vendored `bganim-consumer-contract.json`; none is typed into the harness.

## Finding 1 — the lens names slots, and refuses the ones it does not own

Plane A hidden (and the hide **measured** afterwards via `get_layer_states`, not assumed:
`planeA: false`), 28 sample points across the frame, `pixel_attribution` on each, then the
tile rebased by `BG_TILE_BASE_SLOT`:

- 27 of 28 sample points resolve to plane B
- **13** of them land inside the band's own slot range
- **0** rebase outside the blob in this scene — the out-of-blob path exists and is exercised
  by the harness's own verdict function, but this ROM did not produce one, and the harness
  says so rather than reporting the check as earned.

Corroborated independently of oracle's samples: `tileAddr == tile * 32` holds here too
(`tile 1101` → `0x89A0`).

## Finding 2 — the band steps, and it is not the level scrolling

**A screenshot diff cannot answer this.** A band animates by DMA-ing new *pixels* into fixed
slots, so the nametable tile **index never moves** — across 90 frames, **zero** of the 27
plane-B sample points changed tile id, while the screenshots differed on every capture. Read
naively, those two facts support opposite conclusions, and the screenshot is the more
persuasive one.

The quantity that actually answers it is VRAM tile **bytes** at the band's slots. With a
control run of static blob slots the band does not own (slots 96..127), sampled from the same
paused machine at the same frames:

| frame | band slots 0..31 | control slots 96..127 |
|---|---|---|
| 150 | `980cf21a91b1be04` | `ff44dbe059ec9d2a` |
| 170 | `6fc659806c16bdf6` | `ff44dbe059ec9d2a` |
| 190 | `7a3366c8e8f5b780` | `ff44dbe059ec9d2a` |
| 210 | `9ec7bcb77185fc5f` | `ff44dbe059ec9d2a` |
| 230 | `f24a380741672a51` | `ff44dbe059ec9d2a` |
| 250 | `b3fbbc242e063713` | `ff44dbe059ec9d2a` |

**6 distinct band contents across 6 captures; 1 distinct control content.** The band's own
slots are rewritten while blob slots it does not own are byte-stable over the identical
frames. That separates *the band stepping* from *the level scrolling* and from *a wholesale
background art reload*, neither of which could leave the control run fixed.

The harness states the undetermined case explicitly: had the control moved too, it reports
**UNDETERMINED** rather than claiming the band stepped.

## Finding 3 — a correction to a banked cross-lane contract, and it fails SILENTLY

`docs/OVERSEER.md` records `emulator/pixel_attribution` as returning **`cell` hanging off
`winner`**. It does not. On the build measured here `cell` is a **sibling of `winner`** at the
top level of the result; `winner` carries only `{layer}`.

```
result: { winner: { layer: "planeB" }, cell: { tile, tileAddr, palette, hflip, vflip, priority }, … }
```

Everything else in that banked finding is right and is corroborated here — VRAM-absolute
tiles, `tileAddr == tile*32`, the rebase direction, `cell` present iff the winner is a plane
layer (27/27 plane-B winners carried one).

**Why this is worth a correction rather than a shrug:** a consumer written to the banked shape
reads `winner.cell?.tile` and gets `undefined` for every pixel. It does not throw. My first
lens run did exactly this and reported *"27/28 sample points on planeB"* and *"0 sample points
on planeB"* in the same output — two contradictory lines, both produced by a harness that
looked like it was working. The failure is invisible at the call site; only the contradiction
caught it.

The producing lane verified this live against a spawned server, so the values were checked and
the **nesting** was transcribed. That is bar 16's family — a shape claim reads as
transcription rather than as argument, so it gets waved through.

## Not a defect: the server refuses by name

Three param mistakes of mine were each refused with the accepted spelling attached
(`run_frames` wants `frames` not `count`; `read_vram` wants `addr`/`len`, and `addr` must be a
hex string). A gap that refuses by name feeds the queue instead of degrading into a plausible
answer. Recorded as the loud-failure behaviour working.

## What this unblocks

Click-to-identify in the Effects facet now has both halves proven end to end: name the band
and slot under a pixel (finding 1, with the out-of-blob refusal), and show the author that a
band is genuinely stepping (finding 2). The remaining Aurora-side work is surfacing it in the
editor, which is an item to cut, not a question to answer.
