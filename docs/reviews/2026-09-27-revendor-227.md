## 5. Consumer check (run in this worktree's `src`, at the pin)

**(a) The act START POINT.** aeon's clip act declares it in its `clips.json` as a top-level `start` key, either
`{"clip": <id>}` or `{"x", "y", "why"}`. It is read by `tools/clip_rom_bake.py` `act_start` (line 580 at the pin) and
reaches the ROM through the four `act_descriptor.emp` choosers above.
- `grep -rnE 'start_local_x|start_local_y|start_sec_x|start_sec_y|clip_act_start|act_start\b' src` gives **no hits**.
  No Aurora code parses the descriptor's start fields, so the chooser form breaks no reader. The tests that read this
  vendored file (rule-4 constants: `regions-act-constants`, `regions-panel`, and the currency row) passed on the new
  bytes. The other descriptor readers in `src` (section wiring, the parallax config) read aeon's live descriptor at
  project load, and no test here runs them over this fixture. None of them names a start field (the grep above is
  over all of `src`).
- Aurora's aeon loader carries `startPosition` from `project.json` (`src/core/config/s4-config.ts:41`,
  `src/core/project/aeon/load.ts:985`, `src/core/model/s4-types.ts:437`). `grep -rn startPosition src` finds nothing
  else, so no renderer shows or uses it. Recorded for a future consumer: the throwaway `project.json` that
  `clip_rom_bake.py` writes for a clip act copies the SHIPPED act's `startPosition` (line 1952 at the pin), not the
  clip act's `start`. A start marker drawn from `startPosition` on a clip act would be wrong.
- The donor page's manifest writer keeps the key. `src/core/formats/donors/clip-manifest-doc.ts:14-21` ("NOTHING IS

  committed) parsed the pin's `games/sonic4/data/clips/s2_mtz_cpz/clips.json` (3 clips, 2 corridors, keys incl.
  `start`, `anchor_overlay`, `crossing_overrides`), appended a clip, and serialised it. Every non-clip key, `start`
  included, and every existing clip were deep-equal to the input: 1 passed.
- **Verdict: nothing is required.** Showing or editing the start on the donor page is a feature for a look call, and
