## 5. Findings and observations

### 5.1 OBS.DPR: at a scale factor other than 1 the guides and the screen frame are drawn off their hit tests

`redraw` sizes the map canvas's backing store in device pixels and sets `ctx.setTransform(dpr, 0,
0, dpr, 0, 0)`; its docblock: *"every line below it goes on drawing in CSS pixels, unchanged."*
`drawLayerGuides` and `drawScreenFrame` (`src/renderer/canvas/effects-guides.ts`,
`src/renderer/canvas/screen-frame.ts`) each begin with `ctx.setTransform(1, 0, 0, 1, 0, 0)` and then
draw CSS-pixel coordinates, so on a dpr-scaled backing store they land in DEVICE pixels.
`guideAtCanvasY` and `screenFrameEdgeAt` measure CSS pixels.

Measured in final1 (and final2, final3), all in one run:

- **Control, dpr 1:** the report puts the guides at rows 0, 32, 80, 112, 160; the screenshot column
  is cyan at 32.5, 80.5, 112.5, 160.5; a press on row 80 grabs layer 2 (`dragIndex` 2).
- **Emulated 1.35** (`Emulation.setDeviceMetricsOverride`, `devicePixelRatio` 1.35, the same
  window): the report still says 0, 32, 80, 112, 160; the cyan is at 24.07, 59.63, 83.33, 118.89 CSS
  (80 / 1.35 = 59.26). A press ON the drawn line at 59.63 grabs nothing (`dragIndex` null,
  `hoverIndex` null); a press at row 80, where nothing is drawn, grabs layer 2.
- **The frame, emulated 1.35:** the report puts it at x 24 to 344; the only columns of canvas row
  200 that differ between the unlocked scene (no frame) and the locked one are 18.15 and 255.19
  (24 / 1.35 = 17.78, 344 / 1.35 = 254.81). The composite was switched off (tile-animation sub-tab)
  so only the frame's edges differ.

Every natively measured run here read dpr 1, so the owner's screen at 1 does not show this; the
brief and `deviceScale`'s docblock both record 1.35 on this virtual display. Emulation drives the
same code path (`deviceScale()` reads `window.devicePixelRatio`), but it is an emulation, and a real
1.35 display was not seen tonight. Not a gated row: its green state needs a `src` change, which
this parcel may not make. Captures `obs-dpr-native-guides-final1.png`,
`obs-dpr-emulated-guides-final1.png`, `obs-dpr-emulated-frame-ref-final1.png`,
`obs-dpr-emulated-frame-final1.png`.

### 5.2 CL.FONT: the Detach chip is 13px where Chip states 11px

Chip's button (`src/renderer/components/ui/primitives.tsx`) is styled
`{ ...style, font: 'inherit', fontSize: T.tXs, lineHeight: 1, ... }`, with the comment *"font and
line-height are inherited so a chip in a 13px bar is still 11px"*. The enabled Detach chip
computes `font-size: 13px` in every run (dev3, red-cl, final1 to final3); the readout beside it is
11px. A reading of the code, not measured: `style` already carries `fontSize`, so the later
`fontSize` keeps that earlier key position, and `font: 'inherit'`, set after it, resets the size to
the parent's. The disabled Detach (a `<span>`) was not measured for size. This likely applies to
every chip with a handler; only Detach was measured. Not a gated row, for the same reason as 5.1.

### 5.3 The instrument's finding: Xvfb's real pointer leaks into the page

Dev run 2 was poisoned. Xvfb's pointer starts at the screen centre (840, 525), inside the centred
1400x900 window, at client (700, 422). Chromium synthesizes a mouse move at the real pointer from
time to time, and the app saw moves there that no gesture made: the hover bar re-aimed
(`Pos 416, 348`), the paste ghost and the collision preview jumped, the stamp's link hover went to
null, and a guide drag committed world_y 316 (422 minus the canvas top 106) instead of 120
(`logs/dev2.log`). The harness now parks its OWN display's pointer at (1679, 1049), outside the
window, through libX11's `XWarpPointer` (display and `XAUTHORITY` read from its own child
Electron's environment, `:0` refused), and records every mouse event the page receives: a part in
which any event arrives at a position the harness never sent is UNMEASURABLE. Every part of every
final and red run reported none. **Other CDP rigs in `scratchpad/` do not park the pointer**;
sweep-3's rows read DOM text and its drags were none, but any rig that drags on the map can be
moved by this.

### 5.4 Observations, not ruled

- **O1. A locked frame drag writes the session's Y too.** Read as the unlocked scene's frame with
  the toggle on (real View-menu clicks): the session anchor was (0, 0) before the locked-scene drag
  and (24, 288) after it and its Ctrl+Z. `endFrameDrag` writes `setScreenFrame(fd.anchor.x,
  frameYIsVOffset(scene) ? fd.startAnchor.y : fd.anchor.y)`, and `startAnchor` is the RESOLVED
