# Phase 2C Plan B — the resolver

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** `canvas-resolve.ts` — turn a grid-aligned region of pixels into an abstract tile/block/chunk composition, knowing about no document.

**Architecture:** Pure geometry. Cut the region into 8×8 cells, canonicalise each flip-aware through `tile-canon`, intern them into local **handles**, compose 2×2 handle groups into blocks, compose 16×16 block groups into chunks. Deduped by structure. Refuses nothing — the planner (plan C) guarantees the preconditions and owns every refusal.

**Tech Stack:** TypeScript, Vitest. Depends only on `pixel-ops`, `canvas-doc`, `tile-canon`.

**Spec:** `docs/superpowers/specs/2026-08-15-phase-2c-resolve-and-commit-design.md` §3 (`canvas-resolve`), §2 D3, D5.

**Note on format:** this plan is written and executed in one session, so it records contracts, decisions and the test list rather than re-typing every line of implementation. The TDD order and the commit-per-task discipline are unchanged.

## The one design decision this plan settles

**Chunk-cell flips are emitted as zero, and the *planner* pre-mirrors.**

Spec §2 D3.3 requires that a new chunk cell keep the flips of the cell it displaces (`f_old`), because the engine orients the collision heightmap from those bits — emitting `f_new = 0` where `f_old` was a mirror silently collides against the unmirrored shape.

But `f_old` is document knowledge, and the resolver has none. So the split is:

- **The resolver** emits every chunk cell with `xf = yf = false` and blocks in drawn orientation.
- **The planner** sets `f_new = f_old` and interns `mirrorBlock(shape, f_old)` — the block pre-mirrored so that applying the chunk cell's flip reproduces the drawn art.

`mirrorBlock` is pure geometry and lives here. When `f_old` is zero — the common case — it is the identity and costs nothing. Two cells with the same drawn art but different `f_old` produce different blocks; that is correct, and blocks are the roomy tier (422–828 free of 1024), so the split is affordable where the tile tier's would not be.

## Contracts

```ts
export interface ResolvedTile {
  /** Canonical key from tile-canon — equal for two cells that are one tile under some flip. */
  key: string;
  /** The canonical entries themselves, 64 of them, ready to pack into 32 bytes. */
  entries: Uint8Array;
  /** Every entry is 0. The planner maps these to pool tile 0 and never allocates. */
  blank: boolean;
}

export interface ResolvedBlockCell {
  tileHandle: number;
  /** Orientation taking the canonical tile back to what was drawn here. */
  xf: boolean; yf: boolean;
  /** The single palette line this cell draws from; 0 for an all-transparent cell. */
  palLine: number;
}

/** 4 cells, TL TR BL BR — the same order as BlockDef. */
export interface ResolvedBlock { cells: ResolvedBlockCell[]; blank: boolean }

export interface ResolvedChunkCell { blockHandle: number; xf: boolean; yf: boolean }

/** 256 cells, row-major 16x16 — the same order as ChunkDef256. */
export interface ResolvedChunk { cells: ResolvedChunkCell[] }

export interface CanvasResolution {
  tiles: ResolvedTile[];
  blocks: ResolvedBlock[];
  /** One per 256x256 region cell, row-major across the region. */
  chunks: ResolvedChunk[];
}

/** Pixel-space, and 256-aligned. The planner validates; this assumes valid. */
export interface ResolveRegion { x: number; y: number; chunksWide: number; chunksHigh: number }

export function resolveCanvasRegion(
  pixels: PixelBuffer, region: ResolveRegion,
): CanvasResolution;

export function mirrorBlock(b: ResolvedBlock, xf: boolean, yf: boolean): ResolvedBlock;
```

**No `gridOrigin` parameter.** Commit works on whole chunks (§2 D5) and a chunk is 256px, so the region's own origin fixes every cell boundary inside it. Threading `gridOrigin` in as well would give two answers to "where does this cell start" — the constraint overlay's and the resolver's — and they would drift. The planner is responsible for choosing a region the artist's grid agrees with.

### Task 2: compose and dedup blocks

- [ ] **Step 1: Write the failing tests**

- two block positions with identical 2×2 handle/flip/line content intern to one block handle
- blocks differing only in `palLine` are **two** blocks (the line is part of the block cell)
- blocks differing only in a cell's flip are **two** blocks (dedup is exact; only tiles are flip-aware)
- an all-transparent block reports `blank: true`

**Decision recorded:** block dedup is **exact**, not flip-aware. Flip-merging blocks would require knowing the displaced cell's flips to keep collision right (§2 D3.3), which is the planner's knowledge, and blocks are not the scarce tier. Tiles stay flip-aware, which is where the conservation actually matters.

- [ ] **Steps 2–5:** as above.

### Task 3: `mirrorBlock`

- [ ] **Step 1: Write the failing tests**

- `mirrorBlock(b, false, false)` is structurally equal to `b`
- x-mirroring swaps cells TL↔TR and BL↔BR and toggles each cell's `xf`
- y-mirroring swaps TL↔BL and TR↔BR and toggles each cell's `yf`
- mirroring twice in the same axis is the identity (involution — the property the planner relies on)
- `palLine` is carried unchanged, since a mirror moves cells and does not recolour them

- [ ] **Steps 2–5:** as above.
